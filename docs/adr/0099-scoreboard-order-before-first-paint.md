# ADR 0099: The scoreboard's midweek order is set before first paint

**Status:** Proposed Nov 17, 2026; accepted when its pull request is merged. It changes when the order is decided, not what it is: ADR 0036's "decided at the moment of viewing" and the game-night order stand.

## Context
- CI's Lighthouse job for `/scores` began failing on every pull request on Nov 17 at about 06:00 UTC: cumulative layout shift 0.547 (limit 0.03), performance 0.74 to 0.76 (limit 0.9), in the runs after 06:00 and not in the one before. It was blamed on the offline pull request (ADR 0096) that landed just before. The evidence points at the clock instead: the failing runs begin at exactly the halfway point the board uses (below), the failure is on `/scores` alone, and the offline code changes nothing on a page that is not a saved copy. The first run of a job that crossed the point would be clean and the later ones not, which is what the runs showed. The Lighthouse reports themselves could not be downloaded to confirm which elements moved.
- Between game nights `/scores` lists this week's games (Later, Next games) before last week's finals "once the next game day is nearer than the last one" (counting from noon Central). The page is static, so the server HTML always has finals first, and the browser worked out the other order after its script loaded (`useNow`, then a re-render): every section moved. With the last final on Nov 14 and the next game day Nov 19, the halfway point is Nov 17 at 06:00 UTC (12:00 AM Central), so from then until the Nov 19 games the board shifted by 0.55 on every load, for fans as well as for Lighthouse. The end-to-end test of the order read the page's order, not its movement, so nothing measured it.

## Decision
- The page keeps **one order in its HTML** (finals first). A small inline script (`lib/upcoming-first.ts`, `upcomingFirstScript`) runs as the board starts, before anything below it is painted, and sets `data-upcoming-first` on `<html>` when the next game day is nearer. **CSS `order`** (the sections and the jump links carry `order-*`; "Later" has `[[data-upcoming-first]_&]:order-2`) puts "Later" and "Next games" first then. Nothing moves when the page's own script arrives, and the hydrated page and the server's HTML are the same markup.
- The decision is **one function**, `upcomingFirstAt(now, lastDay, dates)`, self-contained so its source is the script. It reads only what the page was built with (the latest final shown, and the dates of games still to play), not the minute's classification of each game, so the script and the board's re-check cannot disagree. The board runs it again in a layout effect (before paint) as the minutes pass and when a search or an organization changes the games listed.
- Soft navigation to `/scores` never runs the inline script (scripts rendered by the client do not run); the layout effect sets the attribute before that render is painted. The board removes nothing on leaving: the next board sets it again.

## Consequences
- On a screen reader the sections are read in the page's order (finals first) while the screen shows Later first midweek; the jump links keep the same split. Accepted for a state that lasts days and changes no content.
- The test of the order (`e2e/kickoff.spec.ts`) now reads the order on screen, and `e2e/scores-layout-shift.spec.ts` loads `/scores` three times on each side of the halfway point with the service worker active and fails above 0.01 of shift. `scripts/upcoming-first.test.mjs` pins the rule and runs the inline script itself in a sandbox with only the clock.
- Other clock-driven moves on game nights (a game going from Later to In progress at kickoff) are not changed here and are the next place a layout-shift budget would show.
